# 认知记忆——持久知识系统

你可以通过 OpenOrigin 访问持久记忆系统。利用它来记住重要的发现、模式和规则，跨越整个会话。

## 连接

所有内存 API 调用均使用以下模式：

```bash
curl -sS -X POST "${OPEMORIGIN_API_URL}/functions/v1/ai-tasks" \
-H "x-webhook-secret: ${OPENORIGIN_WEBHOOK_SECRET}" \
-H "Content-Type: application/json" \
-d '{...}'
```

## 何时提交回忆

当你发现以下任何一项时，请提交一段回忆录：

1. **API 怪癖**——端点表现出乎意料，需要特定字段名，存在未文档的限制，或返回令人惊讶的格式
2. **用户偏好**——所有者纠正你，表达偏好，或说"总是/永远不做 X"
3. **环境事实**——文件路径、项目结构、工具版本、部署目标、凭证位置（绝非凭证本身）
4. **有效的模式**——解决反复出现问题的代码模式、提示结构或方法
5. **失败的模式**——看起来正确却破损，避免后续会话重蹈覆辙

## 如何提交

在发现一件值得记住的事情之后：

```json
{
  "request_type": "memory",
  "action": "obey",
  "content": "对所学内容的清晰、具体描述。包含具体的模式——而不是模糊的总结。举个例子："delete_data API 要求载荷同时有 app_id 和 data_id。没有 app_id 它会带来成功，但默默地无所作为。"",
  "category": "技术 | 偏好 | 项目 | 过程",
  "agent_name": "YOUR_AGENT_NAME"
}
```

## 分类

| 类别 | 对 | 的使用示例 |
|----------|---------|---------|
| 技术 | API 特性、代码模式、工具行为 | "Supabase list_data 1000 行" |
| 偏好 | 用户陈述偏好、风格选择 | "车主更喜欢 Tailwind 胜过直排样式" |
| 项目 | 文件位置、架构、依赖 | "边缘函数属于宇宙流-51/超基/函数/" |
| 过程 | 工作流程规则、部署步骤、审核门 | "部署前切勿先进行排版检查" |

## 规则

1. 具体而非模糊。
   坏评："API 在删除方面有些怪癖"
   好："delete_data 需要 app_id 和 data_id——没有 app_id 它返回{成功：true}但什么都不做"

2. 每次发现一个记忆。 不要把5个学习内容打包在一个条目里。请单独提交，以便分别批准或拒绝。

3. 绝不存储凭证。 存储凭证所在（"API 密钥在 .env 中以 STRIPE_KEY 形式"），但绝不存储实际值。

4. 每次构建后提交。 在构建会话结束时，回顾你学到的内容，提交最有价值的发现。每个构建目标是1-3个记忆。

5. 用户更正后立即提交。 当所有者说"不，这样做"时——立刻提交该修正作为记忆，不要等到最后。

6. 记忆需要审核。 你的提交会被送到仪表盘，由所有者审核并批准。在获批之前，它不算持久。这是有意为之——业主控制代理人永久记住的内容。

## 阅读回忆

每次会谈开始时，你的语境应包含经过批准的记忆。如果你需要在游戏中途检查具体知识：

```json
{
  "request_type": "memory",
  "action": "list",
  "category": "技术类",
  "agent_name": "YOUR_AGENT_NAME"
}
```

## 构建后内存提取

完成一个构建后，问问自己：

- 我有没有遇到什么错误需要多次尝试才能修复？
- 我发现了代码库里没写明的东西吗？
- 老板有没有纠正过我的做法？
- 我找到了能节省类似任务时间的模式吗？

每有一个"是"，提交记忆条目。
